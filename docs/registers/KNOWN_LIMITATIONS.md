# Known Limitations

> Things the **platform** prevents, distinguished from things that are broken.
>
> Consulted at **design time** (do not design a flow on an unavailable capability) and at **test
> time** (a matching case is skipped with its ID, never failed).

---

## Two rules that keep this register trustworthy

**1. An entry requires a reference proving the platform blocks it.**
No reference, no entry. Without this rule the register fills with bugs misfiled as limitations,
and then the real entries stop being believed — which is worse than having no register.

**2. Nothing is hard-deleted.**
A resolved limitation moves to the resolved section, dated, with what resolved it. Old
screenshots, old support answers and old test cases still refer to it.

| KL-005 | Supabase / PostgREST (the live project, i.e. every user not on fixtures) | Reading more than **1000 rows** in one request — and being TOLD when a reply was cut short | PostgREST wraps every request in `LIMIT <max-rows> OFFSET <n>`; this project's `max-rows` is 1000. A request that hits the ceiling is **not an error**: it answers `200` with exactly 1000 rows, and supabase-js reports `error: null`. Nothing distinguishes that reply from a table that genuinely holds 1000 rows, so the truncation is invisible to the caller. The cap cannot be raised from the client — PostgREST takes the SMALLER of `max-rows` and any `.limit()` the request asks for. | The live project's own edge logs, 10-Sep-2026: every `GET /rest/v1/attendance_records` answers `response.headers.content_range = "0-999/*"`, against a week holding 2,220 matching rows. `pg_stat_statements` carries the generated statement, `... The control's `accessibilityLabel` still reaches a screen reader (`aria-disabled` IS emitted), so the reason is available to a reader and to nobody else. | `node_modules/react-native-web/dist/exports/Pressable/index.js` — `styles.disabled = { pointerEvents: 'box-none' }`, `useHover(hostRef, { disabled, ... })`, and `_tabIndex = disabled ? -1 : 0`; `node_modules/react-native-web/dist/modules/useHover/index.js` lines 121–152, where every `add*Listener` is passed `null` when disabled. | Nothing — the affordance IS delivered, by the workaround below. | **Wrap the control, do not decorate it.** A `View` around the disabled control sees what the control cannot: `pointerenter` fires on an element when the pointer moves into it or any descendant, and `pointerdown` bubbles, and RN Web forwards the whole pointer family on a View (`modules/forwardedProps`, `clickProps`). `src/components/Tooltip.tsx` is that wrapper. | KL-007 | react-native-web 0.21 (the web platform, i.e. every user) | Raising an element above content that is drawn LATER and lives outside its subtree — a tooltip, a popover, any overlay hung on a control in the middle of a screen | RN Web writes `position: relative` **and** `z-index: 0` onto essentially every `View`. A positioned element with a numeric z-index creates a stacking context, so almost every node in the tree is one, and a z-index set inside a subtree can only order things WITHIN that subtree. It cannot lift anything past an ancestor's later sibling: at equal z-index the later element wins, and the ancestor's own `z-index: 0` seals its children in. Measured on the built page: the tooltip's ancestry ran `bubble[z=20] → wrapper[z=30] → row[z=5] → eleven × DIV[z=0, relative]`, and a member card that is a later sibling nine levels up painted straight over it. Raising the bubble to 20, the wrapper to 30 and the row to 5 were each a no-op. | The built page, 11-Sep-2026: `.evidence/reset-tooltip-browser.txt` records the ancestry dump, the three failed z-index attempts and the pixel sample that detected the occlusion. | Nothing — the overlay IS shown, by the workaround below. | **Hang it UPWARD, and stop reaching for z-index.** What sits above a row came EARLIER in the document, so an overlay extending over it paints on top by document order alone, with no z-index anywhere. `src/components/Tooltip.tsx` anchors at `bottom: '100%'` for exactly this reason and carries no z-index at all. **A z-index here is not merely unnecessary, it is misleading** — it looks like it works and does nothing, and nothing in a source-reading spec can tell the difference. Any overlay that genuinely must go downward has to be proved in a browser first: `.harness/reset-tooltip.mjs` samples the pixel with the overlay up and down, which is the only check that distinguishes "drawn" from "drawn underneath something". `rung: src/components/resetTooltip.test.ts` (no z-index, anchored above). | `src/components/Tooltip.tsx` (covered); every future overlay that is not a `Modal` |
| KL-008 | The local harness (`db/harness/`), i.e. every `npm run test:db` run and the CI `db-harness` job | Asserting anything about **GRANTS, default privileges or role membership** — `has_function_privilege`, `has_table_privilege`, `pg_default_acl`, and anything that depends on who can execute what | The harness builds its own roles in `db/harness/000_local_shim.sql`, which ends with `alter default privileges in schema public grant all on functions to anon, authenticated, service_role`. A real Supabase project's default privileges are the platform's and are configured differently — and are changed by the platform over time, independently of this repository's migrations. So a privilege assertion in `supabase/tests/` is answered by the shim, not by the thing it is about, and it can pass locally while the opposite is true in production. **This is not a bug in the harness.** It cannot reproduce a configuration it does not have; the harness proves a migration well-formed BY RECONSTRUCTION, which CLAUDE.md says in as many words. | `supabase/tests/48_course_week_day_status.sql` asserts `has_function_privilege('anon', 'public.course_week_day_status(uuid, date, uuid)', 'EXECUTE') = false` and PASSED, 12-Sep-2026. The function was then applied to production and its ACL read `anon=X/postgres`. Both facts are recorded in `.evidence/0067-anon-grant-found-in-production.txt`, with the before-and-after ACLs. | A privilege assertion that passes for the wrong reason — which is worse than an absent one, because it reads like proof (RC-042). | **Check the migration TEXT, not the harness.** The text is the one thing identical in both places: `src/data/migrationGrants.test.ts` asserts that every function granted to `authenticated` also carries an explicit `revoke … from anon`, and lists the 23 that do not with the reason each is currently safe. **Keep the SQL assertions as well** — they are still worth having against a harness that may one day mirror the platform — but never treat one as evidence about production. The only thing that IS evidence about production is reading the ACL there, after the apply, which is the step CLAUDE.md already mandates and which is what caught this. | `src/data/migrationGrants.test.ts` (covered, for functions); table and column grants, role membership and RLS-policy *privileges* are uncovered — the RLS policies themselves are covered by the SQL suite, which does not depend on the shim's grants |

## Maintenance triggers

1. **Discovered during build** → add the entry immediately, with its reference and the
   customer-facing answer. A limitation found and not recorded will be rediscovered, expensively.
2. **A workaround fully resolves it** → move to Resolved, dated, with what resolved it.
   A *partial* workaround edits the row and keeps it Active.
3. **A change removes or alters an affected module** → update the affected-modules column.
   An entry with zero remaining modules is retired to Resolved ("feature removed", dated).
4. **A matching test unexpectedly PASSES** → flag the entry "VERIFY — possibly expired".
   **Never retire it mid-run**; the periodic review owns retirement, with fresh research.
5. **Periodic review** — before each release, or monthly: re-verify every active entry. Platforms
   ship. A limitation from two years ago is often no longer true, and a stale entry silently
   removes a capability from your product.
