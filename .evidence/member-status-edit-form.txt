Built-page evidence - the Status field on the Edit member form
Recorded 06-Sep-2026 for requests/2026-09-06-member-status-in-edit-form.md

The .harness/ scripts are Linux-only (they hardcode /opt paths), so this was
run the way this machine can run it: `npm run export`, the dist/ tree served
statically, and Playwright 1.63 driving the BUILT page - the same artifact a
browser would get. Both themes are forced through the stored preference
(`rosifit.theme.mode`), not through prefers-color-scheme, because that is what
ThemeProvider actually reads: emulating the colour scheme alone left both runs
rendering dark, which is why the first pass reported identical colours for
"light" and "dark" and proved nothing.

Fixtures: member 1 (Divya, active), member 5 (Nithya, inactive).

TWO DEFECTS THIS FOUND, both fixed before the run below:

  1. `accessibilityState={{ selected }}` produced NO attribute at all on the
     built page - role="radio" with no checked state, so a screen reader
     announced both choices as unpicked. This is the same React Native Web
     0.21 hole `src/components/Dropdown.tsx` already documents; the fix is the
     same, `aria-checked` written directly.

  2. Space did not operate the control. React Native Web's Pressable answers
     Enter and lets Space through to the page - the keydown was observed
     arriving at the element with no press following it. Space is the key that
     picks a radio (CP-22, and the ARIA pattern before it), so the two choices
     now carry their own handler. The two controls beside them on this form -
     the day chips and the primary-address radios - do NOT answer Space
     either, and expose no checked state; that is pre-existing and untouched
     here.
